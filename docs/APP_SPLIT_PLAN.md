# Hermoso Mobile: Splitting One App Into Two (Customer / Business)

Status: executed. `android-customer/`, `android-owner/`, `ios-customer/`, and `ios-owner/` are scaffolded and role-pure — see §7/§8 for what changed vs. the original single-app plan below. `android/` and `ios/` are kept read-only as reference until both platforms are verified end-to-end, then deleted per §4.
Scope: `android/` and `ios/` only. `server/` and `client/` (web admin) are unaffected.

## 1. Why

Today both Android and iOS ship **one** binary that branches on `userRole` at runtime
(`"salon_owner"` vs everything else) to decide theme, bottom nav, start screen and which
screens are even reachable. The client now wants **two separate installable apps** —
a customer app and a salon-owner ("business") app — not a single app with a role switch.

The repo already anticipates this split: `android/hermoso_customer_app.html` and
`android/hermoso_business_app.html` are titled *"Hermoso — Customer App"* and
*"Hermoso — Business App"*, so that naming is adopted below.

## 2. Current state (verified from code)

**Android** — single Gradle module, single app:
- `android/settings.gradle.kts` → `include(":app")` only.
- `applicationId = "com.example.myapplication"` ([build.gradle.kts](../android/app/build.gradle.kts)) — a placeholder id, never rebranded.
- One `MainActivity`, one `NavHost` in [HermosoApp.kt](../android/app/src/main/java/com/example/myapplication/app/HermosoApp.kt) containing every customer *and* owner route.
- Role branching happens in three places in that same file: `Scaffold.containerColor` (Cream vs `PurpleDeeper`), the post-login/post-splash start destination, and `BottomNav`'s item list.
- Theme (`ui/theme/Color.kt`) is **not** actually two distinct palettes today, despite appearances: `OwnerNavy`/`OwnerGold`/`OwnerTextLight` are defined but never referenced by any screen, and `AppHeader`'s `isOwnerTheme` parameter is dead (it doesn't branch on anything in the function body). The *only* real owner-vs-customer visual difference in the current app is `Scaffold.containerColor` (`PurpleDeeper` full-screen background for owner vs `Cream` for customer) — both from the same purple family. Corrected after starting the split; see the migration notes below.

**iOS** — single Xcode project generated by XcodeGen, single target:
- `ios/project.yml` defines one target `Hermoso`, bundle id `com.hermoso.ios`.
- [ContentView.swift](../ios/Hermoso/App/ContentView.swift) is a 20-line router: after splash, if `session.userRole == "salon_owner"` show `OwnerShellView`, else `CustomerShellView`.
- `Views/Customer/`, `Views/Owner/`, `Views/Shared/` are already cleanly separated folders — this is the single biggest thing that makes the iOS split low-risk.
- `ios/context/*.md` (ARCHITECTURE.md, SCREENS.md, THEME.md, DATA_MODELS.md, API_REFERENCE.md) is living documentation, already written to be the source of truth for the iOS build — worth preserving and duplicating into both new iOS projects rather than discarding.
- `ARCHITECTURE.md` §6b flags **dead code that must not be carried forward**: `ScanCameraScreen.kt`/`ScanCameraComponents.kt` (fake-progress camera flow, never captures a real photo) and `ScanResultsComponents.kt`'s section composables (unused dark-theme results variant). The live equivalents are `ScanScreen.kt`/`ScanResultsScreen.kt`. This split is a natural point to drop that dead code from Android too instead of copying it into the new customer app.

**Backend** — already role-aware, no structural change needed. `server/middleware/rbac.middleware.ts` gates routes by `role` (`customer`, `salon_owner`, `admin`, `super_admin`); login returns the user's `role` in the response body already.

**Push notifications**: none implemented yet (no FCM/APNs found in the repo) — notifications are polled via REST. So there's no dual-push-project setup to worry about for this split; flag it as a follow-up whenever push is added later.

## 3. Decisions made for this plan

Confirmed with you:

| Question | Decision |
|---|---|
| Repo strategy | **Same repo**, 4 new self-contained top-level folders — no new git repos, no shared source module between the two apps (full duplication, not a shared library) |
| Naming | **Hermoso App** (customer) / **Hermoso Business** (owner) |
| Cross-role login | Each app **rejects** a login from the wrong role with a clear in-app error |

## 4. Target layout

```
Hermoso-main/
  android-customer/     new Gradle project — Hermoso App (customer)
  android-owner/        new Gradle project — Hermoso Business
  ios-customer/         new Xcode project (XcodeGen) — Hermoso App (customer)
  ios-owner/             new Xcode project (XcodeGen) — Hermoso Business
  android/               kept read-only as reference until both Android apps are verified, then deleted
  ios/                    kept read-only as reference until both iOS apps are verified, then deleted
  server/                 unchanged
  client/                 unchanged (web admin, has its own admin/owner roles — out of scope)
  docs/
```

Each of the 4 new projects is a fully standalone build: its own Gradle project / Xcode
project, own app id, own icon, own theme, own nav graph, own copy of networking + DTOs +
utils. Nothing is `import`ed across the four — that's the tradeoff of "no shared module"
you picked, in exchange for zero risk of one app's change silently affecting the other.
Section 8 covers how to keep the four copies from drifting apart.

## 6. Android migration

1. **Scaffold two new Gradle projects**, `android-customer/` and `android-owner/`, each a
   copy of the current `android/app` structure (`build.gradle.kts`, `settings.gradle.kts`,
   `gradle/`, manifest, `res/`) with `applicationId` set per the table above and a
   fresh `rootProject.name`.
2. **Copy source, split by ownership**, dropping the two role-branch points instead of
   porting them:
   - Customer app gets: `HomeScreen`, `ScanScreen`, `ScanResultsScreen` (+ `ScanModels`),
     `MatchScreen`, `RecommendationsScreen`, `TrackerScreen`, `BookingScreen`,
     `BookingListScreen`, `SalonsScreen`, `SalonServicesScreen`.
   - Owner app gets: `OwnerDashboardScreen`, `OwnerCalendarScreen`, `OwnerServicesScreen`,
     `OwnerClientsScreen`, `OwnerInsightsScreen`.
   - Both get their own copy of: `AuthApi.kt` (Retrofit client, DTOs, `SessionManager`),
     `AuthScreen.kt`, `AppHeader.kt`, `ProfileScreen.kt`, `NotificationScreen.kt`,
     `CalendarComponent.kt`, `SkeletonComponents.kt`, `SplashScreen.kt`, `DataModels.kt`,
     `ui/components/StatusBadge.kt`, `utils/DateTimeUtils.kt`, `utils/LocationUtils.kt`.
   - **Drop, don't copy**: `ScanCameraScreen.kt`, `ScanCameraComponents.kt`,
     `ScanResultsComponents.kt` (confirmed dead code, see §2).
3. **Rewrite `HermosoApp.kt` per app** — each becomes a plain single-role `NavHost`:
   remove the `when (userRole)` branches entirely (`Scaffold.containerColor`, start
   destination, `BottomNav` items collapse to one hardcoded list each). Post-login/post-
   splash always routes to that app's one start destination.
4. **`ui/theme/Color.kt` and `Theme.kt`** — both apps use the same purple-family palette
   (confirmed that's what's actually applied today, not a real navy/gold theme — see §2).
   Drop the unused `isOwnerTheme` parameter from `AppHeader.kt` in both copies (it never
   did anything). Remove the unused `OwnerNavy`/`OwnerGold`/`OwnerTextLight` tokens from
   the customer app's `Color.kt`; keep them in the owner app's as unused-but-available in
   case a real navy/gold redesign happens later.
5. **New launcher icon for the owner app** — customer app can reuse the existing
   `mipmap-*/ic_launcher*` assets as-is; the owner app needs a navy/gold icon designed
   and dropped into its own `res/mipmap-*` set (flagging this as a design dependency, not
   something to fabricate here).
6. **Login-role guard** (see §8) added to each app's `AuthScreen.kt`.
7. Build both (`./gradlew :android-customer:app:assembleDebug`, ditto for owner),
   smoke-test against the shared backend, then remove `android/` once both are verified.

## 7. iOS migration

Lower risk than Android because `Views/Customer`, `Views/Owner`, `Views/Shared` are
already separated on disk.

1. **Scaffold two new XcodeGen projects**, `ios-customer/` and `ios-owner/`, each with
   their own `project.yml` (copy of `ios/project.yml`) — set `PRODUCT_BUNDLE_IDENTIFIER`,
   `CFBundleDisplayName`, and target name per app.
2. **Copy source, split by ownership**:
   - Customer app gets `Views/Customer/*`, `Views/Auth/AuthView.swift`, `Views/Onboarding/*`,
     the customer-only `Shared/` views (camera/scan-related: `CameraPreviewView`,
     `FaceOverlayView`, `ScoreRingView`, `FlowTagsView`, `ResultCard`, `SalonCardView`,
     `EventCardView`), matching `ViewModels/`, and `Models/DTOs/{Booking,Event,Salon,Scan,Service}DTOs.swift`.
   - Owner app gets `Views/Owner/*`, `Views/Auth/AuthView.swift` (its own copy),
     the owner-relevant `Shared/` views (`CalendarView`, `SummaryRowView`, etc.), matching
     `ViewModels/Owner*ViewModel.swift`, and `Models/DTOs/OwnerDTOs.swift`.
   - Both get their own copy of: `Services/{AuthApi,NetworkService,SessionManager,Config}.swift`,
     `Models/DTOs/{Auth,Common,User}DTOs.swift`, `Models/Enums/Enums.swift`, `Utils/*`,
     the app-chrome `Shared/` views (`AppHeaderView`, `BottomNavBar`, `NotificationsView`,
     `ProfileView`, `EmptyStateView`, `ErrorRetryView`, `ShimmerView`, `SkeletonComponents`,
     `StatusBadgeView`, `SectionHeaderView`, `LabeledSelect`).
   - Some `Shared/` files need a quick per-file check against `ios/context/SCREENS.md`
     during the copy to confirm which side(s) actually use them — the split above is
     derived from the current view tree but SCREENS.md is the tie-breaker if a file's
     usage isn't obvious from its name.
3. **Simplify `ContentView.swift` per app** — delete the `session.userRole ==` branch;
   each app's `ContentView` goes straight from splash/auth to its one shell
   (`CustomerShellView` or `OwnerShellView`).
4. **Duplicate `ios/context/*.md` into both new projects**, trimmed to that app's screens —
   this documentation is genuinely useful and cheap to carry forward; don't drop it.
5. **App icon**: customer app can reuse `Assets.xcassets/AppIcon.appiconset` as-is; owner
   app needs a new navy/gold icon (same design dependency as Android §6.5).
6. **Login-role guard** (see §8) added to each app's `AuthView.swift`.
7. `xcodegen generate` in each new folder, build both schemes, smoke-test, then remove
   `ios/` once verified.

## 8. Sign-up role picker must also be removed

Confirmed in code: Android's `AuthScreen.kt` (lines ~229–262) has a customer/salon-owner
toggle on the registration form (`selectedRole`, defaults to `"customer"`); iOS's
`AuthView.swift` should be checked for the same. Once split, each app should register
users as its own fixed role only — delete the toggle, hardcode `role = "customer"` in
the customer app's sign-up request and `role = "salon_owner"` in the owner app's. This
is a small but necessary part of §6/§7's `AuthScreen`/`AuthView` copy step, not optional.

## 9. Login-role guard (no backend change required)

Each app already receives `user.role` in the `/auth/login` response. Add one check,
client-side, in both apps' auth flow, right after a successful login and before saving
the session:

- Hermoso App (customer) expects role `customer`. If the response role is `salon_owner`
  (or `admin`/`super_admin`), don't call `SessionManager.saveSession`, show
  *"This is a business account — download Hermoso Business to sign in."* and stay on
  the login screen.
- Hermoso Business (owner) expects role `salon_owner`. If the response role is
  `customer`, show *"This is a customer account — download Hermoso App to sign in."*

This needs zero backend changes since the role is already returned. If you later want
server-side enforcement too (e.g. so a stolen token can't be replayed against the wrong
app), that would mean adding a client-type header/claim and checking it in
`auth.middleware.ts` — worth doing eventually, not required for this split.

## 10. Keeping four duplicated codebases from drifting

Full duplication (your choice in §3) trades shared-module safety for isolation. To keep
that manageable:
- Treat `server/` route/DTO shapes and `ios/context/API_REFERENCE.md` /
  `ios/context/DATA_MODELS.md` as the single source of truth for the wire format; when
  the backend changes a response shape, update all four client copies, not just one.
- Keep the two backend-agnostic docs (`API_REFERENCE.md`, `DATA_MODELS.md`) duplicated
  identically into both iOS projects (and consider writing Android equivalents) so there's
  one thing to diff when checking the four copies are still in sync.
- No code-level tooling is proposed here (e.g. a codegen step from an OpenAPI spec) since
  none exists in the repo today — flagging it as a future option if drift becomes painful,
  not part of this plan.

## 11. Store & release considerations (not part of the code split itself)

- Two Play Store listings, two App Store Connect listings, two sets of screenshots —
  the existing HTML mockups are a reasonable starting point for store screenshots.
- Two Android signing keys, two iOS provisioning profiles/certs.
- Two version numbers/release cadences going forward, since they're now independent apps.
- Owner app icon and any owner-specific store copy still need to be designed — not
  something this plan produces.

## 12. Suggested order of work

1. iOS split first (lower risk — folders already separated, well-documented in `ios/context/`).
2. Android split second, using the same customer/owner file mapping as a checklist.
3. Remove the sign-up role picker and add the login-role guard, in both apps (§8, §9).
4. New owner app icon (design dependency) dropped into both owner projects.
5. Smoke-test both apps end-to-end against the existing backend (no backend changes needed to start).
6. Delete `android/` and `ios/` once both replacements are verified working.
